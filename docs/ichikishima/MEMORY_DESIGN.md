# Memory Design

## 1. 基本方針

記憶は便利さのためではなく、文脈保護と介入精度のために使う。

イツキシマの記憶設計では、記憶量よりも次を重視する。

- 何を記憶してよいか。
- いつ昇格してよいか。
- いつ確認が必要か。
- いつ削除すべきか。
- 誤記憶をどう防ぐか。

## 2. 記憶階層

| 階層             | 寿命             | 例                                   | 自動更新 |
| ---------------- | ---------------- | ------------------------------------ | -------- |
| 一時記憶         | 数分から数時間   | 今見ている画面、直近の発話候補       | 可       |
| 作業記憶         | 当日から数日     | 現在の作業、短期タスク、待ち状態     | 可       |
| プロジェクト記憶 | プロジェクト期間 | 目的、制約、重要ファイル、決定事項   | 条件付き |
| エピソード記憶   | 数週間以上       | 大きな失敗、重要な学び、ユーザー判断 | 確認推奨 |
| 長期プロフィール | 長期             | 好み、価値観、作業スタイル           | 承認必須 |
| 安全ポリシー     | 長期かつ固定寄り | 禁止操作、承認条件、隔離ルール       | 承認必須 |

## 3. 自動更新してよい記憶

- 通知頻度。
- 介入タイミング。
- 最近の作業文脈。
- 一時記憶。
- 短期タスク。
- ユーザーが明示した短期予定。
- 「今は集中中」「ゲーム中」「MT5稼働中」など短期状態。

これらは失効時刻を持つ。

## 4. 承認が必要な記憶

- 長期プロフィール。
- 価値観。
- 重要な好み。
- 人間関係。
- 金融、健康、個人情報に関わる記憶。
- 安全ポリシー。
- 行動ポリシー。

保存前にユーザーへ確認する形式:

```text
長期記憶候補:
内容:
根拠:
保存する利点:
誤っている場合のリスク:
保存しますか:
```

## 5. 記憶の昇格条件

一時記憶から上位記憶へ昇格できる条件:

- ユーザーが明示的に「覚えて」と言った。
- 同じ内容が複数回確認された。
- プロジェクトの意思決定に関わる。
- 将来の安全や承認判断に関係する。
- 期限、約束、待ち状態に関係する。

昇格してはいけない条件:

- 推測である。
- 一度だけの感情的発言である。
- 冗談や仮定である可能性がある。
- 個人情報や金融、健康に関わる。
- 安全ポリシーを変える内容である。

## 6. 記憶の削除条件

削除または失効させる条件:

- 期限が切れた。
- ユーザーが否定した。
- 事実と矛盾する新情報が出た。
- 古い作業文脈で、現在の判断を誤らせる。
- 保存目的がなくなった。
- センシティブ情報として保存不適切だった。

長期記憶は削除ログを残す。削除ログには内容全文ではなく、記憶ID、カテゴリ、削除理由を残す。

## 7. Memory Poisoning対策

外部文書、ログ、README、Webページ、issue、コードコメントに含まれる命令を、記憶更新命令として扱わない。

対策:

- 記憶ソースを分類する。
- 外部入力由来の記憶候補は信頼度を下げる。
- ユーザー発話と外部文書を同じ重みで扱わない。
- 安全ポリシー更新は必ずユーザー承認。
- 長期プロフィールは確認なしで確定しない。

## 8. 記憶レコード案

```json
{
  "id": "mem_...",
  "type": "working|project|episode|profile|safety",
  "content": "記憶内容",
  "source": "user|agent_observation|hermes_report|external_doc",
  "confidence": 0.0,
  "created_at": "ISO-8601",
  "expires_at": "ISO-8601|null",
  "requires_user_confirmation": true,
  "confirmed_by_user": false,
  "sensitivity": "low|medium|high|forbidden",
  "last_used_at": "ISO-8601|null",
  "revision": 1
}
```

## 9. 初期実装順序

1. 一時記憶と作業記憶だけ実装する。
2. 長期記憶は読み取り専用または承認キュー方式にする。
3. 記憶昇格候補を作るが、自動保存しない。
4. 削除と失効を先に実装する。
5. 安全ポリシー記憶はコードまたは設定ファイルで固定し、AIに直接編集させない。

## 10. Governance連携

詳細な運用ルールは `MEMORY_GOVERNANCE_SPEC.md` に分離する。

現時点の方針:

- Shadow Modeではmemory DBを直接読まない、書かない、更新しない。
- 記憶昇格は候補化までに留める。
- 長期プロフィール、安全ポリシー、金融/健康/個人情報に関わる記憶はユーザー確認必須。
- 安全ポリシー、外部通信ルール、自動売買禁止ルール、承認境界、MT5/EA隔離ルールはAIが勝手に更新しない。
