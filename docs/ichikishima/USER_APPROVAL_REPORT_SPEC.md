# User Approval Report Spec

## 1. 目的

ユーザーはコードを読めない前提で、目的・リスク・承認可否を判断できる必要がある。

そのため、Hermesやイツキシマが変更案を作成した場合、コード差分とは別に、非エンジニア向けの変更レポートを必ず出す。

## 2. 禁止表現

禁止:

- 「問題ありません」
- 「安全です」
- 「完全に確認済みです」
- 実行していないテストを実行済みと書くこと
- 未確認項目を隠すこと

推奨表現:

- 「この範囲では問題を検出していません」
- 「未確認項目があります」
- 「この操作は低リスクですが、戻し方は以下です」
- 「本体反映には承認が必要です」

## 3. 変更レポート形式

```text
【変更レポート】

1. 何をしたか
- 一言で説明

2. なぜ必要だったか
- 目的
- 解決した問題

3. どこを変更したか
- 変更ファイル
- 変更範囲
- 触っていない重要領域
- Sandbox内作業か、本体反映候補か

4. ユーザーに見える変化
- UIの変化
- 挙動の変化
- 設定の変化

5. リスク
- リスクレベル: 低 / 中 / 高 / 原則拒否
- 壊れる可能性がある箇所
- 既存機能への影響
- セキュリティ上の注意
- 高リスク領域に触れたか

6. テスト結果
- 実行したテスト
- 成功/失敗
- 未確認項目
- 実行していないテスト

7. 戻し方
- 失敗した場合の復旧手順

8. イツキシマの判定
- 承認推奨 / 保留 / 却下推奨
- 理由

9. ユーザーに求める判断
- 承認して反映
- 保留
- 修正して再試行
- 破棄
```

高リスク領域に触れていない場合も、「触っていない」と明示する。何も書かれていない状態を安全扱いしない。

## 4. リスク説明の粒度

リスクは「怖そうな言葉」ではなく、ユーザーが判断できる形にする。

リスクレベル:

| レベル | 意味 | 承認 |
|---|---|---|
| 低 | Zone内またはドキュメントのみ。既存挙動への影響がほぼない | 原則不要または一括承認 |
| 中 | 本体repoへの限定反映。戻し方がある | 要承認 |
| 高 | 設定、依存、外部通信、記憶、ユーザー通知に影響 | 明示承認 |
| 原則拒否 | 秘密情報、MT5/EA、memory DB直接編集、git push、本番反映、破壊的操作 | 別タスクで明示指示がない限り不可 |

承認疲れを避けるため、低リスクのSandbox内作業は細かく承認を求めない。ユーザーに求めるのは、本体反映や高リスク境界越えの判断だけにする。

悪い例:

```text
リスク: 既存機能に影響する可能性があります。
```

良い例:

```text
リスク:
- 設定読み込み処理を変更したため、起動時の設定反映に影響する可能性があります。
- チャット画面や記憶DBには触っていません。
- 外部送信処理は変更していません。
```

## 5. テスト結果の書き方

必ず分ける。

- 実行したテスト。
- 成功したテスト。
- 失敗したテスト。
- 実行していないテスト。
- 確認できていない項目。

例:

```text
6. テスト結果
- 実行したテスト: npm test -- settings
- 結果: 成功
- 未確認: Windows実機でのインストーラ動作
- 実行していないテスト: E2Eテスト、外部連携テスト
```

## 6. 触っていない重要領域

高リスク領域を触っていない場合は明示する。

例:

```text
触っていない重要領域:
- .env / APIキー
- memory DB
- MT5 / EA関連ファイル
- 本番環境
- git push
- 外部送信
```

触った場合は、イツキシマ判定を原則「保留」または「却下推奨」にする。特に秘密情報、MT5/EA、memory DB直接編集、git push、本番反映は、通常の承認レポートだけで進めない。

## 7. イツキシマ判定基準

承認推奨:

- 目的に合っている。
- 変更範囲が限定されている。
- 禁止領域に触れていない。
- テスト結果と未確認項目が明示されている。
- 戻し方がある。

保留:

- 目的は合っているが、テスト不足。
- 影響範囲が広い。
- ユーザー判断が必要な仕様差分がある。
- 説明が不十分。

却下推奨:

- 禁止領域に触れている。
- 秘密情報、MT5、記憶DB、本番環境へ影響する。
- 外部送信が含まれるのに確認がない。
- 戻し方がない。
- 実行していないテストを実行済み扱いしている。

イツキシマの判定は最終承認ではない。イツキシマは「承認推奨 / 保留 / 却下推奨」を提示し、ユーザーが最終判断を行う。

## 8. 承認疲れを避ける設計

承認を求めるべき時:

- Sandbox外へ反映する時。
- 既存本体を変更する時。
- 依存関係を追加する時。
- 外部送信する時。
- ユーザーへ通知する時。
- 長期記憶やプロフィールを更新する時。
- 本番環境、git push、破壊的操作が関係する時。

承認を求めない時:

- Sandbox内で試すだけ。
- Sandbox内に失敗ログを保存するだけ。
- Sandbox内でテストを回すだけ。
- ドキュメント案を作るだけ。
- 変更レポートを生成するだけ。

承認単位は細かくしすぎない。例えば、同じ目的の本体反映候補は1つの変更レポートにまとめ、ユーザーが「この変更全体を進めるか」を判断できる形にする。

## 9. 承認UIの最小情報

承認画面には最低限これを表示する。

- 変更の一言要約。
- リスクレベル。
- 変更ファイル数。
- Sandbox内か、Sandbox外反映か。
- 承認が必要な理由。
- 触っていない重要領域。
- 実行したテスト。
- 未確認項目。
- 戻し方。
- イツキシマ判定。
- 選択肢。

選択肢:

```text
[承認して反映]
[保留]
[修正して再試行]
[破棄]
```

## 10. 判断可能な粒度のチェックリスト

承認レポートは、ユーザーが次の質問に答えられる粒度でなければならない。

- これは何のための変更か。
- 今すぐ反映する必要があるか。
- どこに影響するか。
- どこには影響しないか。
- 失敗したらどう戻すか。
- 何をテスト済みか。
- 何をまだ確認していないか。
- 高リスク領域に触れているか。
- イツキシマはなぜその判定をしたか。

どれかに答えられない場合、判定は「保留」にする。

## 11. 承認ログ

承認ログには次を保存する。

- 承認ID。
- 対象作業ID。
- レポート本文。
- ユーザー選択。
- 承認日時。
- 実際に反映したファイル。
- 反映後テスト結果。

承認ログに秘密情報を含めない。

承認ログには、ユーザーが何を承認したのかが後から分かるように、承認対象の境界も保存する。

- Zone内作業のみ。
- Sandbox外反映。
- 本体repo反映。
- 外部送信。
- 高リスク操作。
