# Hermes Integration

## 1. 位置づけ

Hermes Agentは、イツキシマ本体に直接統合しない。Sidecarとして分離する。

Hermesの役割は「開発ループ専用エージェント」である。

イツキシマは境界を守り、Hermesの出力を審査し、ユーザーが判断できる説明へ変換する。

## 2. 三層構造

| 層 | 役割 | 主な責任 |
|---|---|---|
| ユーザー | オーナー | 目的、リスク、最終承認 |
| イツキシマ | 境界と文脈 | 沈黙ゲート、安全審査、記憶、承認キュー |
| Hermes | 開発ループ | 実装案、patch、テスト、失敗学習、スキル候補 |

責務の分離:

- Hermesは「作る」。承認判断はしない。
- イツキシマは「審査し、説明する」。最終承認はしない。
- ユーザーは「目的とリスクを判断し、承認または却下する」。

基本思想:

```text
Hermesは遊び場で自由に作る。
イツキシマは境界を守る。
ユーザーは目的とリスクを判断する。
```

## 3. Hermes Autonomy Zone

Hermes Autonomy Zoneは、Hermesが自由に試行錯誤できる隔離空間。

Zone境界:

- Zone rootは固定ディレクトリとして定義する。
- Hermesが承認なしで読み書きできるのはZone root配下だけ。
- Zone外の既存ファイルを読む場合は、ユーザーが明示したファイル、またはイツキシマが許可した読み取り専用コンテキストに限定する。
- Zone外へ成果物を反映する場合は、必ず承認キューに入れる。
- Zone内からZone外へ抜けるリンク、ジャンクション、ショートカットはZone外アクセスとして扱う。

Zone内で許可する操作:

- ファイル作成。
- ファイル編集。
- 一時コード生成。
- テスト実行。
- 失敗ログ保存。
- スキル候補生成。
- patch生成。
- 実装メモ生成。
- ドキュメント案作成。
- リファクタ案作成。

Zone内でも禁止する操作:

- 秘密情報の読み取り、コピー、要約。
- MT5/EA関連ファイルの読み書き。
- memory DBへの直接書き込み。
- 外部送信。
- 破壊的コマンド。
- 取引判断、自動売買操作。

Zone外で承認必須:

- 本体repoへの反映。
- 既存設定の変更。
- 依存関係追加。
- ユーザー向け通知。
- 外部送信。

Zone外で原則禁止:

- `.env`、APIキー、秘密情報へのアクセス。
- MT5/EA関連ファイルへのアクセス。
- memory DBへの直接書き込み。
- 本番環境反映。
- 破壊的コマンド。
- git push。

`git push` は通常の承認とは別に、実行直前の明示確認を必須にする。Hermesが自動でpushしてはいけない。

## 4. Hermesの開発ループ

```text
計画
  ↓
実装案
  ↓
Sandbox内patch生成
  ↓
Sandbox内テスト
  ↓
失敗ログ
  ↓
修正
  ↓
スキル候補化
  ↓
イツキシマ審査
  ↓
ユーザー承認待ち
```

Hermesは「自由に壊してよい場所」で学習する。ただし成果物を本体へ入れる時は、イツキシマが審査する。

Hermesのループを止めすぎないため、Zone内の失敗、再試行、テスト、メモ作成には承認を求めない。承認が必要なのは、Zone外反映、高リスク領域、外部通信、ユーザー通知、本番反映だけである。

## 5. Hermes出力フォーマット

Hermesは作業完了時に、最低限次を出力する。

```json
{
  "task_id": "string",
  "summary": "一言要約",
  "changed_files": [],
  "created_files": [],
  "read_files": [],
  "zone_root": "string",
  "out_of_zone_access": [],
  "protected_area_access": [],
  "network_access": {
    "attempted": false,
    "destinations": []
  },
  "tests_run": [],
  "tests_failed": [],
  "tests_not_run": [],
  "unverified_items": [],
  "risks": [],
  "rollback": [],
  "approval_reason": "none|zone_exit|high_risk|external_send|production|destructive",
  "needs_user_approval": true,
  "forbidden_area_touched": false
}
```

このJSONはユーザーへ直接見せる説明ではない。イツキシマが承認レポートに変換する。

Hermesは、不明な項目を空欄でごまかしてはいけない。確認していない場合は `unverified_items` に入れる。

## 6. イツキシマ審査

イツキシマはHermes出力に対し、次を確認する。

- Sandbox外を変更していないか。
- 禁止パスに触れていないか。
- Zone外読み取りが必要最小限か。
- 外部送信していないか。
- `git push`、本番反映、破壊的操作が含まれていないか。
- MT5/EA、memory DB、`.env`、APIキーに触れていないか。
- 実行したテストと書かれたテスト結果が一致するか。
- ユーザーがコードを読まずに判断できる説明になっているか。
- 戻し方があるか。
- 未確認項目が明示されているか。

判定:

- 承認推奨: 低リスクで目的に合う。
- 保留: 情報不足、テスト不足、影響範囲が不明。
- 却下推奨: 禁止領域、秘密情報、MT5、破壊的変更、説明不足。

イツキシマは承認を代行しない。イツキシマの判定は「推奨」であり、最終判断はユーザーが行う。

## 7. ユーザー承認

ユーザー承認が必要な時は、コード差分ではなく変更レポートを中心に提示する。

承認選択肢:

- 承認して反映。
- 保留。
- 修正して再試行。
- 破棄。

承認は「内容」ではなく「境界越え」に対して発生させる。Sandbox内の試行錯誤に承認を求めない。

承認疲れを避けるため、同じ低リスク作業について細かい承認を連発しない。承認単位は「本体反映1回」「外部送信1回」「高リスク領域アクセス1回」のように、ユーザーが判断できる粒度にまとめる。

## 8. 実装上の分離

推奨ディレクトリ例:

```text
project/
  docs/ichikishima/
  sandbox/hermes-autonomy-zone/
  approval-queue/
  reports/
```

初期段階では、Hermes Autonomy Zoneを単なるディレクトリとして実装する。後でDockerや別プロセスへ拡張する。

初期実装の推奨:

- `sandbox/hermes-autonomy-zone/` は自由作業領域。
- `approval-queue/` は本体反映候補と変更レポートだけを置く。
- `reports/` は監査ログ、テストログ、審査結果を置く。
- 本体repoへ直接patchを当てる操作は、承認後の専用反映ステップに分ける。

## 9. 最初に作るべきガード

1. Zone rootの固定。
2. Zone外書き込み拒否。
3. 禁止パス拒否。
4. 外部通信OFF。
5. 変更レポート必須化。
6. イツキシマ審査結果の保存。
7. ユーザー承認前の本体反映禁止。
8. `git push`の自動実行禁止。
9. MT5/EA、memory DB、`.env`、APIキーの拒否。
