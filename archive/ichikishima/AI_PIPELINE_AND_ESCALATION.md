# AI Pipeline And Escalation

## 1. 基本方針

ローカルLLMだけで全てを解決しようとしない。

ローカルAIは普段の脳。ハイエンドAIは難所突破の専門医。

イツキシマ、Hermes、Cursor、GPT-5.5、Claude Code、Codexは役割を分ける。

## 2. 通常時

通常時はイツキシマのみ軽量常駐する。

役割:

- 状況観察。
- 沈黙ゲート。
- 通知判定。
- 短文応答。
- 最近の作業文脈維持。

想定モデル:

- 小型Qwen系。
- 小型Gemma系。
- VRAM 12GBで常駐可能な軽量モデル。

## 3. 開発時

開発時はHermesを起動する。

役割:

- タスク分解。
- 実装案生成。
- Sandbox内patch生成。
- テスト案生成。
- テスト実行。
- 失敗ログ保存。
- スキル候補生成。

Hermesは本体へ直接反映しない。Sandbox内成果物をイツキシマが審査し、ユーザー承認へ回す。

## 4. MT5稼働中

MT5稼働中はリソース競合と操作事故を避ける。

方針:

- Hermes停止。
- 重いLLM停止。
- 市場見守りは軽量処理のみ。
- 取引判断、自動売買操作、EA変更はしない。

## 5. ゲーム中

ゲーム中は推論を停止または通知のみにする。

方針:

- 重いモデル停止。
- GPU負荷を抑える。
- 緊急でない通知は後でまとめる。

## 6. ローカルでやること

- 要件整理。
- 軽い修正。
- テスト追加。
- ドキュメント更新。
- タスク分解。
- 定型実装。
- 日次レビュー。
- 伴走。
- 承認レポートの下書き。

## 7. ハイエンドAIへ渡す条件

次のいずれかを満たす場合、GPT-5.5、Claude Code、Cursor、Codexなどへエスカレーションする。

- Hermesが2回以上失敗した。
- 根本原因が不明。
- アーキテクチャ変更が絡む。
- セキュリティが絡む。
- MT5/EAまわりで誤りが損失につながる。
- 非同期処理や依存関係が複雑。
- 差分が大きい。
- 仕様解釈に曖昧さがある。
- 「それっぽいが不安」が残る。

## 8. 失敗時のパスルール

```text
ローカル軽量AI
  ↓ 低リスクなら継続
Hermes Sandbox
  ↓ 2回失敗 or 不安あり
ハイエンドAI
  ↓ 変更案
イツキシマ審査
  ↓
ユーザー承認
  ↓
本体反映
```

## 9. コストと難易度による使い分け

| 作業 | 推奨 |
|---|---|
| 短い整理、通知判定 | イツキシマ軽量LLM |
| ドキュメント下書き | ローカルLLMまたはHermes |
| 小さなコード修正 | Hermes Sandbox |
| 複数ファイルの設計変更 | Cursor / GPT-5.5 |
| セキュリティ境界 | GPT-5.5 / Claude Code |
| MT5/EA高リスク判断 | ハイエンドAI + ユーザー明示承認 |
| 本番反映 | ユーザー承認必須 |

## 10. 初期実装順序

1. 軽量イツキシマの沈黙ゲート。
2. Hermes Autonomy ZoneのSandbox。
3. 変更レポート生成。
4. イツキシマ審査。
5. 承認キュー。
6. ハイエンドAIへのエスカレーション記録。
7. 可視化。

モデル連携より先に、安全境界と承認レポートを作る。
