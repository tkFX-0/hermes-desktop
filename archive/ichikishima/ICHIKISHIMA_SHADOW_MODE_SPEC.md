# Ichikishima Shadow Mode Spec

## 1. 目的

Ichikishima Shadow Modeは、イツキシマ本体の最小実装段階である。

この段階では、イツキシマはユーザーへ自動発話せず、通知もせず、memory DBも更新しない。目的は、Hermesの変更レポートや作業状態を観察し、危険度と話す価値を判定するための土台を作ることである。

## 2. Shadow Modeの定義

Shadow Modeとは、イツキシマが「黙って見て判断する」状態である。

できること:

- 状態を観察する。
- 判断候補を作る。
- Hermes変更レポートを審査する。
- 危険度を判定する。
- 話す価値があるかを判定する。
- 可視化イベント候補を出す。

まだしないこと:

- 自動発話。
- 音声出力。
- 通知。
- memory DB更新。
- 外部通信。
- MT5/EA連携。
- Hermes本体操作。
- UI実装。

## 3. 状態定義

- `idle`: 待機。
- `observing`: 状況を観察している。
- `recalling`: 関連文脈を参照している。ただしmemory DB直接更新はしない。
- `judging`: 介入価値や危険度を判定している。
- `silent`: 話す価値が低いため沈黙する。
- `speak_candidate`: 発話候補はあるが、自動発話しない。
- `approval_review`: Hermes変更や承認候補を審査している。
- `blocked`: 禁止領域や高リスク操作を検出した。

## 4. 話す価値がある時だけ話す判定方針

Shadow Modeでは、発話候補を作っても自動発話しない。

判定に使う観点:

- 緊急性。
- ユーザー損失リスク。
- 作業中断コスト。
- 根拠の強さ。
- 同じ内容を最近出していないか。
- 禁止領域や高リスク操作に関係するか。

## 5. 自動発話しない方針

Shadow Modeでは `shouldSpeak:false` を既定にする。

発話候補がある場合も、ユーザー向け通知や音声出力は行わない。記録とレビュー候補の生成までに留める。

## 6. memory DBを直接更新しない方針

Shadow Modeでは、memory DBを読まない、書かない、更新しない。

長期プロフィール、安全ポリシー、価値観、個人情報、金融/健康情報に関する記憶更新は、この段階では扱わない。

## 7. Hermes変更レポート審査の方針

Hermes変更レポートから次を確認する。

- 禁止領域に触れていないか。
- 実行したテストが明記されているか。
- 未実行テストが明記されているか。
- 次工程が危険境界へ進まないか。
- 「問題ありません」と断定していないか。
- ユーザーが判断できる粒度か。

判定は `approve_recommended`、`hold`、`reject_recommended` の候補として返す。ユーザー最終承認を代替しない。

## 8. 可視化イベント候補

Shadow ModeではUIを作らず、将来の可視化用イベント型だけを用意する。

候補:

- Observe。
- Recall。
- Judge。
- Silent。
- SpeakCandidate。
- ApprovalReview。
- Blocked。

イベントにはcontent本文や秘密情報を含めない。

## 9. 禁止領域

- 既存EA本体。
- MT5関連。
- `.env`、APIキー、secrets。
- memory DB。
- 外部通信。
- git push。
- 本番設定。
- 自動売買関連。
- 取引履歴。
- 個人情報。
- 自動発話、通知、音声出力。

## 10. 次の実装順序

1. 状態モデルの型定義。
2. 沈黙ゲートの安全側スタブ。
3. Hermes変更レポート審査仕様。
4. Hermes変更レポート審査スタブ。
5. 可視化イベント型。
6. Shadow Modeのテスト。
